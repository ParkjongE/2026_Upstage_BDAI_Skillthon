# 신발 분석 예시 — 다중 네이버 코드라 실 API를 시도하지 않는 케이스

## 요청 예시

```
신발 카테고리 요즘 검색 늘어난 게 진짜 뜨는 건지 봐줘.
```

## 실행 명령

```
python scripts/run_pipeline.py --category 신발 --period-months 48
```

## 기대 로그

```
[2] 데이터 로드
    -> 데모 데이터 사용: 카테고리 매핑이 실데이터 자동 분석 대상이 아닙니다:
       검증완료 (다중코드: 자동 합산 보류) (n=48개월)
```

## 왜 데모로 나오는지 (중요 — API 실패로 오해하지 말 것)

`reference/category-mapping.md`에서 `shoes`는 네이버 코드가
`50000173`(여성신발), `50000174`(남성신발) **2개**다. 이 두 상대지수를
그냥 더하거나 평균 내면, "최댓값=100 기준 상대지수"라는 정의 자체가
깨져서 숫자가 무엇을 의미하는지 불분명해진다(BOUNDARY 원칙). 그래서
`try_fetch_real_data()`는 `len(row["naver_codes"]) != 1`인 카테고리는
**API를 호출하지도 않고** 바로 데모 데이터로 대체한다 — 이건 네트워크
오류나 인증 실패가 아니라 의도된 안전장치다. 로그 사유 문구가
"다중코드: 자동 합산 보류"이면 이 경로다. (반대로 "실 API 로드 실패:
...")로 시작하면 실제로 API 호출을 시도했다가 실패한 것이다 — 이 둘을
구분해서 사용자에게 설명해야 한다.)

`bags`(가방)도 같은 이유(여성가방/남성가방 2개 코드)로 같은 경로를 탄다.

## 확장하고 싶다면 (지금은 하지 않음)

성별 하위코드 중 하나만 대표로 쓰거나(예: "여성신발 지수" 라고 명확히
표기), 두 코드를 각각 별도로 분석해 보여주는 방법이 있다. 둘 다 현재
스코프 밖이며, 하려면 `category-mapping.md`에 새 category_key로 나누는
것이 가장 안전하다(예: `shoes_women`, `shoes_men`) — 기존 `shoes` 키의
동작을 바꾸면 "다중코드는 자동분석 안 함"이라는 문서화된 약속이 깨진다.
