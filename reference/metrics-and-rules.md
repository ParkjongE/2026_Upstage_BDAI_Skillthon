# 지표 정의 및 분석 규칙

## 핵심 지표

**검색지수 (search_index)**
- 출처: 네이버 데이터랩 **쇼핑인사이트**(`shopping/v1/categories`)만 쓴다.
  `scripts/naver_client.py`에 "검색어트렌드"(search-trend) 엔드포인트 상수가
  남아있지만 실제로 호출하는 코드는 없으므로, 리포트나 대화에서 데이터
  출처를 말할 때 "검색어트렌드"를 함께 언급하지 않는다 (실제로 안 쓰는
  API를 출처로 표기하면 부정확함).
- ⚠️ 절대 검색량이 아니라 조회 기간 내 최댓값=100 기준 상대지수. 카테고리
  간 절대 비교 금지, 같은 카테고리 내 시간 흐름 비교에만 사용.

**거래액 (revenue)**
- 출처: 통계청 온라인쇼핑동향조사 — 온라인쇼핑몰 취급상품범위별/상품군별거래액
  (통계표 `DT_1KE10041`), 단위 억원, 월별 집계 (절대값)

**추세(trend) / 계절성(seasonal) / 잔차(residual)**
- 방법: 전역 선형회귀(전체 구간에 대한 1차 회귀직선)로 trend 산출 →
  (원계열 − trend)를 같은 달(1~12월)끼리 **중앙값**으로 묶어 seasonal 산출 →
  residual = 원계열 − trend − seasonal
- 이동평균이 아니라 전역 선형회귀를 쓰는 이유: 국소 이동평균은 급증
  이벤트 자체가 그 시점의 추세 계산에 포함돼(로컬 오염) 그 이벤트의
  잔차를 과소평가하게 만든다. 전역 추세는 한두 달의 이상치가 전체
  기울기에 주는 영향이 작아 이 문제를 줄인다.
- 계절성분도 평균이 아닌 중앙값을 쓰는 이유는 이상탐지와 동일
  (평균은 이상치 자체에 끌려가지만 중앙값은 덜 흔들린다).
- 이상탐지는 반드시 **residual에만** 적용한다 (원계열에 바로 적용하면
  계절적 성수기가 전부 "이상"으로 오탐됨)

**이상 이벤트(anomaly event)**
- 정의: |residual의 로버스트 Z-score| > z_threshold (기본값 2.0)
- Z-score는 median/MAD(median absolute deviation) 기반으로 계산한다
  (`0.6745 * (x - median) / MAD`). 평균/표준편차 기반 Z-score를 쓰지
  않는 이유: 이상치가 여러 개 섞이면 표준편차 자체가 커져 서로의
  이상치 정도를 희석시키는 masking 문제가 있어, 이상 이벤트가 한
  시계열에 여러 번 있을 수 있는 이 분석에는 부적합하다.

**신호(signal) / 노이즈(noise) 라벨**
- 이상 이벤트 발생 후 1~2개월 뒤 거래액이 계절 기대치(seasonal 기준
  예상 거래액) 대비 revenue_threshold(기본 +10%) 이상 증가 → "signal"
- 그렇지 않으면 → "noise"
- 이 라벨은 **과거 이벤트에만** 매길 수 있다 (최신 이벤트는 아직 후행
  결과가 없으므로 라벨링 대상이 아니라 예측 대상)

**신호확률 (signal_probability)**
- min_sample(기본 6건) 이상의 라벨링된 과거 이벤트가 있어야 로지스틱회귀
  학습 및 예측을 수행한다
- 미만이면 확률을 계산하지 않고 "판단 보류, 데이터 부족(n=X)"으로 표기

**과거 이력 요약 (history summary)**
- 최신(미라벨) 이상 이벤트가 없어 위 신호확률을 계산할 수 없는 경우가
  가장 흔하다(대부분의 기간엔 그 시점에 급증이 없는 게 정상). 이 경우도
  리포트가 빈 내용이 되지 않도록, 과거 라벨링된 이벤트 중 실제로 신호로
  이어진 비율(기저율)과, 같은 기간 검색지수의 전반적 추세(상승/하락/보합)
  를 항상 함께 계산해 보여준다(`summarize_history()`). "지금 급증은 없지만
  과거엔 이 카테고리 급증의 N%가 매출로 이어졌고, 전반적으로는 [방향]
  추세"라는 문장이 항상 나온다.

## 안전장치 (모든 리포트에 필수 반영)

1. 데이터가 데모(가상)인지 실제 API 연동인지 리포트 상단에 명시
2. 모든 수치에 표본 수(n)와 기간을 함께 표기
3. min_sample 미만 구간은 확률 대신 판단 보류로 표기
4. "확실히 뜬다/안 뜬다" 등 확정 표현 금지 → 등급형 표현만 사용
   (예: 관찰 필요 / 관심 있게 지켜볼 만함 / 판단 보류)
5. 검색지수(상대값)와 거래액(절대값)을 같은 축·같은 숫자로 직접
   비교하지 않는다
6. 상관관계·시차상관 결과를 인과관계로 서술하지 않는다
   ("~때문에 늘었다"가 아니라 "~시점에 함께 관찰되었다")
7. 이 리포트의 판정은 자동 발주·마케팅 집행 결정을 대신하지 않으며
   검토 후보 제시 용도로만 사용한다고 명시
8. "신호"/"노이즈"/"데모 데이터" 같은 내부 용어를 정의 없이 쓰지 않는다.
   리포트 상단에 쉬운 말로 풀어 쓴 용어 설명(글로서리)을 두고, 판정
   문구 자체도 전문용어보다 쉬운 말이 먼저 보이게 쓴다
   (예: "노이즈 가능성 높음"이 아니라 "반짝 관심(노이즈)일 가능성 높음").
9. "구글트렌드로 나우캐스팅하는 것과 같은 원리" 같은 유추를 쓸 때는
   "같은 원리"처럼 단정하지 말고 "비슷한 원리"로 톤을 낮춘다 — 검색관심도를
   수요 선행지표로 쓰는 연구(Choi & Varian, 2012 등)는 실재하지만, 같은
   방법론군의 가장 유명한 사례(Google Flu Trends)가 실제로는 크게
   과대예측해 비판받은 전례(Lazer et al., 2014)도 있어 "항상 맞는 정설"
   처럼 서술하면 과신이다.

## 실패 시 점검 순서 (가장 흔한 원인부터)
1. **`--category`로 넘긴 문자열이 category_key로 해석되지 않았는가** — 가장
   흔한 실패 원인. `python scripts/run_pipeline.py --list-categories`로
   가능한 category_key/별칭을 확인하고, 해석 실패 로그에 뜬 후보 중
   정확한 값을 다시 지정한다. 이름이 비슷하다고 임의로 category_key를
   추정하지 않는다 (`reference/category-mapping.md` 경계 원칙).
2. 카테고리는 해석됐지만 매핑표 자체에 없는가 → 매핑 추가가 먼저 필요
3. 데이터가 데모로 나왔는가 → 두 가지를 구분한다: (a) 실 API 호출을
   시도했지만 실패(네트워크·인증·프록시 등) — `try_fetch_real_data()`의
   예외 처리 경로, (b) 애초에 실 API를 시도조차 하지 않음 — 네이버
   카테고리 코드가 category당 1개가 아닌 경우(예: `shoes`=신발은
   여성신발/남성신발 2개 코드) 상대지수를 임의 합산하지 않기 위해
   의도적으로 건너뛴 것(`len(row["naver_codes"]) != 1` 분기). (b)는
   버그가 아니라 설계된 안전장치이므로 "API 호출이 실패했다"고 말하지
   않는다 — 로그의 사유 문구로 (a)/(b)를 구분할 수 있다.
4. 계절성 분해 결과에 결측/이상값이 있는가 → 입력 시계열 길이(12개월
   미만은 계절 버킷이 비어 0으로 처리됨)를 확인
5. 라벨링된 이벤트 수가 min_sample 미만인가 → 판단 보류로 전환
6. 리포트에 금지 표현(확정형 문구)이 남아있는가 → 등급형으로 치환
